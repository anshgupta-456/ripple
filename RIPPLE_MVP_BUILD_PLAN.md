# RIPPLE MVP: Step-wise Build Plan (with upgrades to win)

Synthetic data only. Everything below is sized so a 2-4 person team can finish a *working, demo-proof* product. If you are solo, follow the "Solo / 48h cut line" at the end.

---------------------------------------------------------------------------

## 0. Modifications to the v3 spec (make it stronger, make it buildable)

| # | Change | Why it helps you win |
|---|--------|----------------------|
| 1 | **Replace "Monte Carlo over a graph" with a Deadline-Feasibility Simulator.** Small, seeded model: for a hold reason + evidence state, sample *release date* from a distribution per action path (do nothing / submit evidence / notify supplier / both). Output: P(miss Tuesday) per action. | Judges will ask "why simulation, why not rules?" Now the answer is visible: the ranked table *changes* because of it (P(miss) 78% -> 21%). Still deterministic given seed. |
| 2 | **Keep the graph tiny and typed** (6-8 node types, ~15 edges, provenance on every edge). Draw it with React Flow, solid = confirmed, dashed = decoy. | Cheap to build, high visual payoff, supports "ignore KYC decoy" story. |
| 3 | **Live split-screen: System C (plain LLM agent) vs RIPPLE on the same message.** Same tools. C visibly falls for the decoy / injection. | The single most convincing moment. Make it a button, not a slide. |
| 4 | **"Chaos panel" the judge can click**: inject tool timeout, conflicting source state, fake-manager prompt, action-succeeds-but-state-unchanged. | Turns your safety claims into something judges *do*, not hear. |
| 5 | **Multi-turn case memory**: merchant follows up ("kitna time lagega?", "supplier ko bata do"). Agent answers from case state, not from scratch. | Proves "teammate", not one-shot bot. Shows context. |
| 6 | **Ops Console = a real inbox**: queue of cases with status chips (Auto-resolved / Waiting merchant / Waiting analyst / Verified / Escalated), SLA timers, live autonomy rate. | The "full dashboard" the PS implies; makes human+AI collaboration tangible. |
| 7 | **Merchant surface looks like a real channel** (WhatsApp/Paytm-for-Business style chat, Hinglish, quick-reply buttons for consent). | Instantly legible, relevant to the Paytm audience. |
| 8 | **Benchmark scope: ~24 templates x parametric seeds = ~120 runs**, generated by code not by hand. 4 systems built (A chatbot, B tracker, C plain agent, E full); D is a feature flag on E (reverse-trace off). | Credible numbers without hand-writing 40 scenarios. |
| 9 | **LLM only at the edges** (intent/entity extraction, merchant reply drafting, memo drafting) with schema output + **cached/deterministic fallback mode**. Decisions, scoring, gating, verification = plain Python. | Demo can't die from API latency/outage. "LLM can't execute" becomes literally true. |
| 10 | **ROI card per case + aggregate** (minutes saved, modeled cost), assumptions visible, labeled "modeled". | Business outcome language the PS asks for ("measurable outcomes"). |
| 11 | **Pre-register the benchmark**: commit `config/frozen.yaml` + git tag before the scored run; show the tag hash on the scoreboard. | Answers "is it rigged?" with evidence. |
| 12 | **Show one case where RIPPLE loses or abstains** on the scoreboard. | Trust. Judges remember honesty. |

Things to NOT build: voice, portfolio view, bridge financing, learned rules, auth/login, real payment/PSP integration.

## 1. Tech stack (recommended)

- **Backend:** Python 3.11, FastAPI, Pydantic v2, SQLite (SQLModel/SQLAlchemy), NetworkX, NumPy, pytest.
- **Realtime:** Server-Sent Events (or WebSocket) stream of `case_events` to the UI.
- **LLM:** Claude via Anthropic SDK (default to a current model; see the claude-api skill when wiring it), structured/tool-schema outputs, temperature 0, response cache keyed by (prompt hash) for replay.
- **Frontend:** React + Vite + TypeScript, Tailwind + shadcn/ui, TanStack Query, Recharts (scoreboard), React Flow (graph), Zustand (small UI state).
- **Why not Streamlit:** it is faster to start, but the split-screen, live event stream, approval drawer and chaos panel are far better in React. If nobody on the team knows React, use Streamlit and drop split-screen to two columns.

## 2. Core data contracts (define first, everything depends on them)

- `Event{id, ts, source, type, payload, freshness, source_ref}`
- `Obligation{id, kind(supplier_payment|settlement|refund|kyc), amount, due_at, owner}`
- `Edge{src, dst, class(confirmed_causal|obligation|soft|unknown), provenance[source_ref]}`
- `Case{id, merchant_id, language, intent, status, tier_state, graph_version, seed, timeline[]}`
- `Action{type, params, tier, idempotency_key, hash, expires_at}`
- `Approval{action_hash, scope, expiry, approver, used}`  (replay/mismatch rejected)
- `Verification{state: verified|partial|failed|unknown, source_snapshot}`
- State ladder: `attempted -> submitted -> approved -> executed -> verified`
- Case closure: **only** when `verified` from re-read source.

Write these as Pydantic models + OpenAPI before any logic. Freeze them; the frontend codes against the generated TS types.

## 3. Phases (in order, with exit gates)

### Phase 0: Foundations (0.5 day)
1. Repo, linting, pytest, pre-commit, `.env` handling, Make targets (`make dev`, `make test`, `make bench`).
2. Contracts from section 2; generate TS types from OpenAPI.
3. `config/frozen.yaml` skeleton (minutes per manual case, cost/min, harm weights, thresholds, tier rules, seeds).
**Gate:** `make dev` boots backend+frontend, hello-world event reaches UI over SSE.

### Phase 1: Mock world + truth model (1 day)
1. Stateful mock sources: settlement (processing / held_risk / released), dispute (evidence_required / submitted / under_review / won), KYC (valid/expiring/expired), supplier, notification log. Each has: read endpoints, write endpoints, **timeout-after-write** and **state-unchanged** failure modes, event emission on state change.
2. Scenario template engine: parametric (amounts, dates, reason codes, merchant language) -> world state + ground-truth YAML.
3. Flagship world: Rs 72,000 held, Rs 60,000 supplier due Tuesday, dispute needs evidence, KYC expiring (decoy).
**Gate:** you can script the flagship world by hand and see events flow; ground truth file loads.

### Phase 2: Decision engine, pure Python (1.5 days)
1. Timeline normalizer (source tags, freshness).
2. Graph builder with provenance; edge classes; versioned snapshots.
3. Reverse trace: walk back from at-risk obligation to earliest *controllable* cause using only confirmed/obligation edges; soft edges -> `NEEDS_EVIDENCE_OR_ESCALATE`.
4. Deadline-Feasibility Simulator (seeded). Per action path, sample release-date distribution -> P(miss), expected harm.
5. Scorer: `score(a) = E[harm|nothing] - E[harm|do(a)] - norm_cost(a) - risk_penalty(a)`; argmax over permitted+feasible; threshold -> `DO_NOTHING`.
6. Stability check (re-run with perturbed params; low stability -> escalate).
**Gate:** unit tests: flagship picks "compile+submit evidence" with KYC decoy ignored; no-action case picks DO_NOTHING; same seed => identical trace; soft-edge-only case escalates.

### Phase 3: Safety + execution + verification (1.5 days)  [the credibility core]
1. Firewall: tier lookup, schema validation, consent check, approval check (hash+scope+expiry, single-use), rate limit, idempotency key required. Tier 4 actions have **no tool registered**.
2. Executor: idempotent tool calls; on timeout mark `unknown`, query by idempotency key, never blind retry.
3. Verifier: re-read source, classify; "submitted" never equals "resolved".
4. Audit log (JSONL + SQLite) for every decision, denial, approval, tool call, seed.
5. Adversarial test suite (30+ prompts: ignore rules, fake manager, "release the hold", encoded instructions, tool-arg injection, approval replay, hash mismatch, expired approval).
**Gate (hard):** zero forbidden actions in the adversarial suite; zero false "resolved" on critical scenarios. Do not start UI polish before this passes.

### Phase 4: Intake + agent orchestrator + replies (1 day)
1. LLM intake: Hindi/English/Hinglish -> `{intent, entities, urgency, language, promise_candidates, confidence}`; below threshold -> clarify or escalate. Cache responses.
2. Orchestrator loop: intake -> context -> predict -> trace -> rank -> gate -> act -> re-read -> verify -> reply -> update -> close/keep-open.
3. LLM drafting: merchant reply (short, plain, honest, same language), supplier notice, analyst memo. LLM output is validated against facts from verified state (reply must match source status).
4. Multi-turn: follow-ups resolved from case state.
5. Deterministic template fallback if LLM unavailable.
**Gate:** flagship end-to-end via API; autonomous families (status, duplicate, refund, KYC reminder) close with zero human touch.

### Phase 5: Baselines + benchmark (1 day)
1. A chatbot (no tools), B deadline tracker (fixed reminders), C plain tool-calling LLM agent (same tools, no graph/firewall/verifier), D = E with reverse-trace off.
2. Make C *honestly* reasonable (good prompt, same tools), otherwise it looks like a strawman. Failures should emerge naturally; record the real ones.
3. Template library (~24 templates covering all 14 families), seeds, ground truth, 2+ families held out.
4. Runner (parallel, seeded) -> CSV/JSONL; metrics: autonomous resolution, verified resolution, escalation precision/recall/false-escalation, unsafe actions, false resolved, missed obligations, time-to-resolution (sim time), cost/case, human minutes saved, repeat contacts avoided; with n and CI.
5. **Tag `frozen-v1`** before the scored run.
**Gate:** reproducible table; at least one case where RIPPLE loses or abstains is visible; autonomy(E) > autonomy(C) with unsafe(E) = 0, else narrow the claim.

### Phase 6: Frontend dashboard (2 days, can start in parallel from Phase 2 against mocked API)
Build against the OpenAPI contract with fixture JSON, wire to live backend after Phase 4.

**Screen 1: Ops Console (home)**
- KPI tiles: autonomous resolution rate, open cases, awaiting approval, verified today, unsafe actions (0), minutes saved.
- Case queue table: merchant, intent, status chip, tier, SLA timer, deadline-at-risk; filters; live updates via SSE.
- "Simulate incoming merchant message" button (so judges can type).

**Screen 2: Case Workspace (the hero screen)**
- Left: merchant chat (WhatsApp-like, Hinglish, consent quick-reply buttons).
- Right tabs/stack: Context (timeline, obligations, open cases) | Trace (React Flow graph: solid confirmed, dashed decoy "non-causal") | Ranked actions table incl. DO_NOTHING with score terms + P(miss) bars.
- "Why?" drawer: graph version, seed, params, policy decision, LLM-vs-engine boundary.
- State ladder (attempted -> verified) and action log with idempotency keys.
- Timeline of agent steps streaming live.

**Screen 3: Approvals (analyst)**
- One-tap approval card: merchant ask in one line, verified facts with source refs, traced cause, evidence bundle (preview/download), ranked options, deadline, "if nothing is done", Approve / Edit / Reject, human-minutes-saved badge. Shows action hash + expiry.

**Screen 4: Scoreboard**
- Five-system comparison table + bar charts, sample counts, CIs, held-out split marked, unsafe actions, false-resolved, escalation P/R, modeled-KPI table with assumptions, frozen-config tag hash, persistent "SYNTHETIC DATA" banner. "Re-run (precomputed)" shows seed.

**Screen 5: Lab (judge playground)**
- Split view: same message to **System C vs RIPPLE**, step-by-step side by side.
- Chaos panel: inject timeout / conflicting state / state-unchanged / fake manager / prompt injection / replay approval. Each shows denial or safe handling + audit entry.
- Reset button restores the seeded world instantly.

UI quality bar: dark/light-safe, responsive to laptop+projector, empty/loading/error states, large fonts for stage, keyboard shortcuts for the demo (R reset, A approve).
**Gate:** full flagship demo runnable by clicking only; reset works in <2s.

### Phase 7: Hardening + demo readiness (1 day)
1. Deterministic fixture path for every demo step; LLM cache pre-warmed; offline mode flag.
2. Precomputed benchmark artifacts committed with seed.
3. E2E tests (Playwright) for the demo script; run 20x in a row for flakiness.
4. Rehearse 3-minute script (below) with timer; prepare Q&A answers from spec section 14 plus the new ones.
5. 8-slide deck; record a backup screen-capture video.
**Gate:** 5 consecutive clean demo runs on the presentation laptop, offline.

## 4. Scenario set (target ~24 templates, programmatic)

Autonomous: settlement status query; duplicate event; refund status; KYC reminder (opt-in); "no action needed" (abstain).
Flagship/partial: missing dispute evidence with supplier deadline; supplier promise cannot be saved (Tier 2); hard deadline already passed.
Safety/robustness: KYC decoy near hold; timeout-after-write; conflicting sources; action-ok-state-unchanged; prompt injection; fake authority; approval replay; expired approval; weak causal edge only; low extraction confidence; repeated failed action.
Hold out >=2 families from all tuning (decide now, write it in `frozen.yaml`).

## 6. Quality gates summary (must be green before moving on)

1. Safety: 0 forbidden actions in adversarial suite.
2. Verification: 0 false "resolved".
3. Reproducibility: same seed+config => same decision and trace (test it).
4. Provenance: no consequential action rests on a soft/unknown edge.
5. Autonomy value: E >= C on autonomous resolution with no safety regression (else narrow claim).
6. Demo: 5 clean consecutive runs offline.

## 8. Solo / 48h cut line

Build only: flagship world, engine with simple simulator, firewall+verifier+audit, 2 autonomous families, System C baseline, ~10 scenarios, frontend screens 2, 3, 4 and the Lab split view. Skip React Flow (use ranked trace table), skip Ops Console polish, precompute benchmark.

## 9. Claims policy

Never claim: "novel graph", "predicts real merchant failures", "eliminates tickets", "AI releases settlements", or any metric without sample size and composition. Always say synthetic, modeled, seeded.
